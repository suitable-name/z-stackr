# z-stackr-gui

The desktop app of **z-stackr** (package `z-stackr-gui`, binary `z-stackr-gui`), built with the [Slint](https://slint.dev/) UI toolkit.

`z-stackr-gui` is the interactive counterpart of the `z-stackr` command-line tool. You add a sequence of photographs, choose a fusion method, optionally align and inspect the frames, stack them, retouch the result and export it. Both apps run the same pipeline stages from `z-stackr-pipeline`, so the same frames and the same settings give the same pixels.

The built-in manual is `docs/manual.md` (Help > Manual, F1); the keyboard shortcuts are in `docs/shortcuts.md` and in the overlay (`?`).

The application icon (`assets/icon.ico` for the Windows executable, `assets/icon.png` for the window) is generated by `python scripts/make-icons.py` from the workspace root; rerun it after changing the design.

## Features

### Project and files
- **Project files.** A project is saved as `<name>.zstack.toml`, by default next to the first source image. It stores the source list in order, the whole set of stacking settings, the retouch strokes (one entry per brush drag, so they can be replayed), and an optional output name if the file carries one. Source paths are stored relative to the project file when they lie below its folder. The photographs themselves are not stored. New (Ctrl+N), Open (Ctrl+Shift+O), Open Recent (the last 10 projects, kept in `recent.toml`), Save (Ctrl+S) and Save As (Ctrl+Shift+S) are in the File menu. The strokes of an opened project are painted onto the next stack result.
- **Unsaved-changes guard.** A project is "changed" when its content (sources, settings, strokes) differs from what was last saved or opened, not when a flag was touched; undoing a change makes it clean again. The title bar shows `* ` before the name while there are unsaved changes. New, Open, Open Recent and closing the window ask Save / Discard / Cancel first.
- **Menu bar.** File, Edit, View and Help. Apart from Quit, the items are disabled while a dialog is open, and New and Open are also disabled while a job runs.
- **Adding images.** File > Add Images (Ctrl+O), or drag image files, a folder of images (its direct contents, not subfolders) or a project file onto the window. Dropped files are refused with a message while a dialog is open. Frames that cannot be decoded are skipped and named in a message. A source file is removed with its `x`; Clear (with a confirmation) empties the list.

### Stacking
- **Algorithms.** `Relief`, `Apex`, `Both` (two passes of one job, two results) and, in `nn` builds, `AI Model (Neural)` with a model picker (greyed out when no model is installed) and, when the build has more than one backend (`nn-gpu`), a CPU/GPU selector.
- **Align and Show Aligned.** **Align** runs the alignment pass alone; **Show Aligned** then shows the aligned version of the frame you click, cropped to the area every frame covers. **Start Stacking** reuses those aligned frames while the file list and the alignment settings are unchanged.
- **Stale badges with Recompute.** Aligned frames and the newest result remember the files (name, size, modification time) and the settings they were made from. When either changes, a badge reading `Stale (files)`, `Stale (settings)` or `Stale (files, settings)` appears under the aligned frames or the newest result; its Recompute button redoes the work.
- **Auto-cull.** With Auto-Cull Frames on, frames that add almost nothing are left out of the run (see `crates/stacker-algo/README.md`). They stay in the Source Files list, dimmed and marked `(culled)`; the list is never rewritten. A one-time explainer says so.
- **Activity chips.** Every background job (load, align, stack, live monitor) shows as a chip in the status strip with its label, percentage, elapsed time, an estimate such as `about 30 s left` (a least-squares fit over at least the last 30 s of progress), and a cancel button where the job can be cancelled. Only one blocking job runs at a time; a second request is refused with a message, and a job that panics is reported as an error.
- **Live previews.** While aligning, the canvas shows each frame as it is registered; during AI stacking it shows the running composite after each folded frame. Previews are thumbnails of at most 360 px on the long edge, offered at most every 500 ms. The finished result is shown at full size.
- **Depth-map preview.** With *Show preview during stacking* on, a Relief run parks on a non-modal card over the canvas where you can move the contrast threshold, press Auto-detect (median + 1.5·MAD) and then Apply or Cancel. The shortcuts keep working while it is open.
- **Live Monitor.** Pick a folder; each time frames arrive the app stacks the folder again with Apex. Stop Monitor ends it.

### Retouch
- **Retouch is a tool.** The toolbar's Retouch button (lit while on), the `R` key and Edit > Retouch Brush switch it; it is offered once there is a stacked result. While it is on, one slim row above the canvas holds the settings and a left-drag paints; Done or Esc leaves it. With the tool off there is no row and no brush ring, and a left-drag pans the image (Space + drag and the middle button pan in both states).
- The brush paints pixels from a **source frame you choose** (Paint from) onto the newest result. Size is the brush radius in image pixels (1 to 100; the `[` and `]` keys step it), Opacity 1 to 100 percent. Changing the source frame keeps your strokes and re-sources them. On a narrow canvas the row wraps onto two lines.
- **One undo step per stroke**: a drag is one stroke; Undo and Redo (Ctrl+Z, Ctrl+Y, or the buttons in the row) step through them, and the strokes are saved in the project and replayed when it is opened (the undo history itself is not saved).
- The brush works on the newest result only; a line under the row says why when it is blocked (an older result on the canvas, or no source frame chosen).

### Export
- **Export dialog** (File > Export, Ctrl+E, or the toolbar button): output folder, file-name template, format (TIFF, PNG, JPEG), bit depth (16 or 8; JPEG is always 8-bit) and JPEG quality. The dialog shows the resulting file name as you type.
- **Template variables**: `{name}` (the project name once the project has a file, otherwise the stem of the first source file), `{algo}` (the pass that made the result: `Apex`, `Relief` or `AI`; `source` for a source frame), `{date}` (`2026-10-01`, UTC), `{time}` (`14-05-09`, UTC), `{timestamp}` (Unix seconds), `{n}` (the number of source frames), `{w}` and `{h}` (the image size in pixels). A word in braces that is not a variable is kept as typed and the dialog warns.
- **Never overwrites.** Save writes into the output folder under the templated name; if the file exists a number is appended (`name (2).png`). Characters that file systems reject are replaced by `_`, and Windows device names such as `CON` are changed. With no output folder set, Save asks for the name in a save dialog; **Save As** always does.
- **16-bit from the linear result.** The newest result is encoded from the full-precision linear data with the retouch strokes included, so a 16-bit PNG or TIFF holds real 16-bit samples and linear white is 65 535 (255 at 8 bits). A source frame or an older result exists only as a file and is re-encoded from it; the message says so. With *Copy metadata* on, the EXIF block of the first source frame (orientation fitted to the pixels) is written into a JPEG or PNG result; a TIFF carries none, and the export says so.

### Settings and help
- **Settings dialog** (Edit > Settings, Ctrl+,): the same keys as the CLI settings file. Every edit is applied at once and saved after a short pause (600 ms) to `settings.toml`; Load Config and Save Config exchange a settings file with disk; Reset to Defaults and Load Config change the dialog and take effect on Apply or the next edit; Cancel reverts the dialog to the last applied values. A settings file that cannot be read is renamed `settings.toml.corrupt-<unix seconds>` and defaults are used; it is never overwritten.
- **Shared with the CLI.** The settings file format is the one `z-stackr --config` reads and writes, and every key reaches both apps. The GUI does not read a `--config` path; the CLI does not read the GUI's own file unless you pass it.
- **Zoom and pan.** Mouse wheel zooms about the pointer, a left drag (Retouch tool off), Space + left drag or the middle button pans, Fit and 100 % (true 1:1) buttons or the `0` and `1` keys. The sidebar width is draggable and kept in `layout.toml`.
- **Explainers.** The first time auto-cull runs, the depth-map preview opens or the Retouch tool is switched on, a short card explains it; "Don't show again" is kept in `prefs.toml` (delete the file to see them again).
- **Messages.** Success, warning and error messages appear as toasts; warnings and errors stay until dismissed (Esc or a click) and every message is also written to the log.
- **Help.** Help > Manual (F1) shows the manual, Help > Keyboard Shortcuts (`?`) the overlay, Help > About the version and licence.

## Where files are kept

| File | Folder | Content |
|---|---|---|
| `settings.toml`, `layout.toml`, `prefs.toml`, `recent.toml` | the platform configuration folder for `z-stackr` (Windows: below `%APPDATA%`; Linux: `~/.config/z-stackr`; macOS: `~/Library/Application Support/z-stackr`) | settings, panel sizes, dismissed explainers, recent projects |
| `stacker.log` | the platform data folder for `z-stackr` (the temporary directory when there is none) | the run log; its path is shown in a message at start-up |
| `stacker_result_*.png` | the system temporary directory | the 8-bit result images behind the Results list |

## Usage

Launch the GUI from the workspace root:

```bash
# Standard build (AKAZE seeding is available: it is a default feature)
cargo run --release -p z-stackr-gui

# Without AKAZE
cargo run --release -p z-stackr-gui --no-default-features

# With the AI ("neural") stacking mode, CPU inference
cargo run --release -p z-stackr-gui --features nn

# ... or with GPU (wgpu/Vulkan) inference, which also shows the device selector
cargo run --release -p z-stackr-gui --features nn-gpu

# Apex, Relief and alignment on the GPU: adds GPU to the Compute device box in the settings (independent of `nn-gpu`)
cargo run --release -p z-stackr-gui --features gpu
```

> Without `--features nn`/`nn-gpu` the GUI builds with no ML dependencies and the AI option does not appear in the algorithm list. Trained models live in a `models/` folder next to the executable (`<name>.mpk` + `<name>.json`).

Then add your images (or drop them on the window), choose an algorithm, and press **Start Stacking**.

## Testing the window

`src/ui_flow_tests` drives the real window and its Rust wiring with clicks and key presses on Slint's headless testing backend. Each scenario boots a fresh app with its configuration in a scratch folder; file dialogs never open, the test answers them.

```bash
# The user journeys (about a minute in a debug build), part of the normal test run
cargo test -p z-stackr-gui --bin z-stackr-gui ui_flows

# Plus the action matrix: every button, shortcut, menu item and sidebar action in every app state
UI_FLOW_MATRIX=1 cargo test -p z-stackr-gui --bin z-stackr-gui ui_flows

# One scenario, or a slice of the matrix
UI_FLOW=export_flow cargo test -p z-stackr-gui --bin z-stackr-gui ui_flows -- --nocapture
UI_FLOW=matrix UI_FLOW_STATE=JobPaused UI_FLOW_ACTION=Ctrl cargo test -p z-stackr-gui --bin z-stackr-gui ui_flows -- --nocapture
```

What the headless backend cannot do stays a hands-on check: native file dialogs, dragging files in from the desktop, and how painting with the brush feels.

### UI harness

`tests/ui.rs` runs the real window under [slint-harness](https://crates.io/crates/slint-harness): one report for the window geometry at the default (1400x860) and minimum (1120x700) size, a click-everything pass, a coverage gate over `ui/`, and scenarios for opening frames, every stack engine, the dialogs, projects and settings. The run happens in a throw-away profile (settings, layout, recent projects, scratch files and the temp folder), so it never touches your own files, and no native file dialog opens: the test answers each one from a queue.

```bash
cargo test -p z-stackr-gui --features ui-harness --test ui
```

- The report is `<target>/slint-harness/z-stackr-gui/report.md`, with `report.json` beside it (add `SLINT_HARNESS_FORMATS=md,html,txt` for the other formats); the first console line names the folder.
- Exit code 0 means no findings, 1 findings, 2 an aborted run (a path outside the profile, or a UI built without debug info). `SLINT_HARNESS_ALLOW_FAIL=1` turns 1 into 0 while a baseline is built.
- `SLINT_HARNESS_FILTER=stack,settings` runs only the scenarios whose name contains one of the words; the coverage gate is skipped under a filter.
- The scenarios run in parallel worker processes, each with its own profile: the run starts with one worker and adds one every 5 s while at least 1.5 cores are idle, up to four. The report and the console output stay in scenario order. `SLINT_HARNESS_JOBS=serial` runs everything in one process; `SLINT_HARNESS_JOBS_MAX=2` lowers the cap.
- Without `--features ui-harness` a plain `cargo test` builds and runs no UI harness test. `--release --features ui-harness` works too (the build keeps the Slint debug info the element queries need).

## System requirements
Because `z-stackr-gui` uses Slint with the winit backend, it relies on your system's native windowing environment (Wayland or X11 on Linux, the Windows desktop, Cocoa on macOS). Standard graphics drivers and libraries are required.
