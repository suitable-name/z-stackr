# z-stackr-pipeline

The stages of the focus-stacking pipeline, shared by the command-line tool (`z-stackr-cli`) and the desktop app (`z-stackr-gui`). Crate identifier: `stacker_pipeline`.

Every step that both apps need lives here exactly once, as a plain function over explicit inputs. Long stages report through the `Progress` trait and poll the `Cancel` trait; nothing here knows Slint, clap or indicatif. The out-of-core tile loop, with its scratch directory, is the `tiled` module (callbacks for progress, cancel, log, frames and the output); the CLI keeps its progress bars and output-path rules, the GUI its job plumbing and its previews.

| Module | Stage | Settings keys it reads |
|---|---|---|
| `config` | settings text to `StackingSettings` (`from_toml_str` + `sanitized()`, the `bounded` alias, strict or lenient) | all |
| `order` | frame discovery, natural sort, `select_frames` | `stack_every_nth`, `preprocessing.sort_reverse` |
| `load` | `decode_frame` (path) and `decode_frame_bytes` (file contents; `decode_frame` reads the file and calls it): EXIF orientation, rotation, crop, resize, linear planar `f32`; `preprocessed_dimensions` | `preprocessing.*` |
| `align` | `align_dispatch`, `align_frame` (seed, refine, invert, warp, coverage), `Seeder`, `align_sequence` | `alignment_mode`, `bounded_search`, `akaze_seeding` |
| `crop` | `CommonCoverage`, `common_rect`: the rectangle valid in every frame | |
| `cull` | focus census and the cull decision (`plan`, `plan_with`, `plan_frames`, `plan_frames_with`, `census_from_store`, `census_from_frames`); `CullRule` | `auto_cull`, `auto_cull_threshold_pct`, `sort_by_sharpness` (the apps decide whether to cull) |
| `fuse` | `apex`, `relief` (guided, or `relief_multigrid` with the flag), `relief_tile`, `relief_threshold`, `strata`, `strata_on`; `DepthVotes` and `relief_multigrid_tile` for tiled multigrid runs | `pyramid_levels`, `use_all_color_channels`, `grit_suppression`, `relief_*`, `strata_*` |
| `tiling` | tile grid and apron from the settings (`Geometry`, `apron_for`, `Method::{Apex, Relief, Strata, Neural}`) | `pyramid_levels`, `relief_estimation_radius`, `relief_smoothing_radius` |
| `tiled` (not on `wasm32`) | the out-of-core run as callbacks: `run_tiled`, or the pieces `plan_run`, `align_into_store`, `frame_order`, `fuse_tiles` / `fuse_tiles_with` / `fuse_tiles_by`; `Hooks` (progress, cancel, log), `TileFrames`, `TileSink`, `ScratchDir` | `tile_size`, `crop_to_common_area`, all stage keys |
| `output` | `encode`, `EncodedImage`: rounded 8/16-bit sRGB, crop, PNG/TIFF/JPEG as bytes (`to_bytes`) or files (`save`, the same encoders) | `image_saving.output_format`, `bit_depth`, `jpeg_quality` |
| `session` | the in-memory run: `load_frames` over a `FrameSource` (`BytesSource`, `PathSource`), `align_frames`, `cull` (and the standalone `sort_frames_by_sharpness`, `cull_frames`, `run_sort_cull`), `reorder`, `fuse_apex`, `fuse_relief` (or `relief_focus_max` + `relief_finish` around a threshold decision), `fuse_strata` / `fuse_strata_with`, `crop_result`, `estimate_peak_bytes`, `fit_pre_resize` (`PassKind::{Apex, Relief, Strata}`) | all stage keys |

`order` also has the name-only forms for callers without a file system: `natural_sort_names` and `select_frame_names` apply the rules of `natural_sort` and `select_frames_by` to file names.

The `session` module is what the desktop app and the browser worker (`z-stackr-web`) both call for a run with every frame in memory; it has no thread, clock or Slint, and the crate builds for `wasm32-unknown-unknown`. `load_frames` decodes sequentially (the worker is single-threaded); the desktop keeps its parallel `decode_frames` with the same skip and size rules. `estimate_peak_bytes` is the table below as a function (frames, source size, settings, passes: the largest of load, align, cull and fusion, in `u64`); `fit_pre_resize` finds the largest Pre-resize percentage, in steps of 5, that fits a memory budget.

`image_saving.filename_template` and `default_output_dir` are resolved by the CLI's `resolve_output`; the desktop app applies them in its export dialog. `relief_show_preview` is the desktop app's contrast preview. `copy_metadata` is read by nobody. `config::parse_settings(text, Leniency)` is the one settings loader: the CLI uses `Leniency::Strict` (a wrongly typed value stops the run), the GUI `Leniency::Lenient` (the key keeps its default and a warning is shown).

## Behaviour that is decided here

* **One alignment mode table** (`align::align_dispatch`): `translation` never fits scale or rotation, bounded or not; `registration` is the single-resolution bounded registration with the edge-clamped warp in both apps; `none` leaves every frame untouched (no seed is applied). The refiners return a reference-to-source matrix; `align_frame` warps with its inverse and returns that applied matrix with the coverage mask. A failed refinement continues from the (similarity-reduced) seed, and a matrix that cannot be inverted or a warp that fails returns the frame unwarped; both are reported as a fallback, not an error.
* **One decoder.** `load::decode_frame` applies the EXIF orientation of JPEG files unless `ignore_exif_orientation` is set, then `pre_rotation`, the crop and the resize. Alpha is dropped and no colour profile is applied.
* **One frame order.** Frames are in natural file-name order (`frame_2` before `frame_10`); files whose name contains `stacker_result_` and any path in the caller's exclusion list (the CLI passes its output file and log file) are not frames; `sort_reverse` reverses the list, then every `stack_every_nth`-th frame is kept. The first frame is the alignment reference.
* **The `Relief` threshold is a whole-image property.** `fuse::relief_threshold` is evaluated once on the whole-image focus map; tiled callers pass the resulting value to `fuse::relief_tile`. The auto-detection (median + 1.5 MAD of the non-zero focus values, `auto_detect_threshold`) applies with or without the preview, and `session::auto_contrast_pct` (the preview's start value) is the same number the run turns into its threshold.
* **The multigrid `Relief` solves on whole-image planes** (`relief_use_multigrid`, default off; the guided filter stays the default and is bit-identical to before). The planes are the best focus value and the winning frame of every pixel (`fuse::DepthVotes`, 6 B/px); a tiled run folds the **interior** of every tile into them, solves the depth map once (about 28 B/px at the peak, no frame in memory then) and composites every tile with its window of the depth (4 B/px kept), so the result has no seams and does not depend on the tile size. The depth is a position in the frame list: keep the frames in capture order (`sort_by_sharpness` off). The focus maps are computed on the CPU, one frame at a time.
* **`Strata`** (`strata_base_radius`, `strata_detail_focus`) streams over the frames in two passes; its working set is 150 B/px whatever the frame count (`stacker_algo::strata::strata_bytes_per_pixel`), plus the frames in memory runs; a tiled run holds 174 B per padded pixel (the 150 and the two tile frames it reads on demand), never a tile of every frame, and does not read ahead. `fuse::strata_on` and `session::fuse_strata_with` take the caller's `StrataKernels`, which is where a GPU implementation plugs in; what it declines runs on the CPU.
* **The tile loop reads ahead and the alignment can decode ahead.** `tiled::fuse_tiles` (and `fuse_tiles_prefetch`) read the padded tiles of all frames in parallel and, with `Prefetch::Auto` (the default; `Prefetch::Off` for the serial loop), read tile `t + 1` on a second thread while tile `t` is fused. Frames that cannot be shared between threads, a single-tile run and a caller that is a rayon worker read serially. The result does not depend on the timing, and a cancel is polled before every tile, so it still ends the run with `PipelineError::Cancelled`. `align_into_store_overlapped` and `run_tiled_overlapped` decode the next frame on a second thread while the current one is aligned (a `Send` frame source; the same tiles bit for bit). The memory price of both is in the tables below.
* **A cropped result can be resized back out of core.** `TiledOutput::finish` crops the sink and, with `resize_cropped_to_original`, resamples it to the canvas: for a `PlanarImage` sink with `resize_planar` (linear planes), for an `EncodedImage` sink with `EncodedImage::resize` (the same Catmull-Rom spline on the encoded samples, equal to the planar path within one 8-bit code on smooth content).
* **The apron follows what is computed** (`tiling`). `Apex` needs `4 * (2^(L-1) - 1) + 1` pixels rounded up to a multiple of `2^(L-1)`: **128 px for 6 levels, 256 for 7, 512 for the default 8**. The tile size is rounded up to the same multiple, so every padded tile starts on the whole image's decimation grid. `Relief` needs `estimation + 2 * smoothing + 1` (at least 2). `Strata` needs **101 px** whatever its keys (the saliency reach plus two box filters of radius 45, and at least the largest base radius). The neural mode uses `APRON_PX` (128).
* **One cull decision.** `cull::plan` applies `min(2, 50 / N)` percent to the focus census, or with `auto_cull_threshold_pct > 0` exactly that percentage (`CullRule::Fixed`, not scaled by the frame count); the CLI builds the census tile by tile from its tile store, the GUI runs `optimize_stack`, and a test pins that both give the same order. The survivors are fused in stack order; with `sort_by_sharpness` in the census (nearest-neighbour) order. `session::sort_frames_by_sharpness` and `cull_frames` are the GUI's standalone Sort and Cull actions.
* **One encoder.** Linear white is exactly 255 / 65 535 in both apps.
* **One place decides where the heavy stages run** (`compute::Compute`): `apex`, `relief` / `relief_tile` / `relief_focus_max`, the alignment objective (`alignment_device`, handed to the refiners by `align::align_sequence_on` and `align_frame_with_compute`) and the final warp (`warp`). `compute_device = "cpu"` (the default) is the CPU code (`fuse::apex`, `fuse::relief`, `stacker_align`). `"gpu"` in a build with the `gpu` feature tries the device first: no adapter gives the CPU from the start with a notice; a call whose device memory estimate exceeds `GPU_BUDGET_BYTES` (3 GiB, because wgpu cannot report the size of video memory), or a setting the kernels do not cover (a Relief focus radius above 100), goes to the CPU for that call only; pyramid levels under 64k pixels are evaluated on the CPU, where they are faster; a device error, a panic or non-finite values in the result give up the GPU for the rest of the run (the alignment objective falls back per evaluation, and the backend is given up after the frame), reset the shared device so the next run opens a fresh one, and leave one notice with the reason. The CPU result is the reference; the GPU agrees within a small tolerance, not bit for bit. The fallback rules are tested with scripted backends in every build, and against a real device (with failures injected) when an adapter exists.
* **One colour model.** `stacker_core::color::LUMA_CHROMA_FORWARD` / `LUMA_CHROMA_INVERSE` (BT.601 on linear RGB) are the only matrices.

## Memory and disk: per-pixel figures

All figures are bytes per **source pixel** `P = W * H` unless marked otherwise. A `f32` planar frame has three planes, **12 B/px**. `N` is the number of frames, `T` the tile size, `A` the apron, and `Q = (T + 2A)^2` the pixels of one full padded tile. Border tiles are smaller, so the tile figures are upper bounds.

### CLI and `tiled` (out-of-core)

`tiled::TiledPlan::scratch_bytes` and `fusion_ram_bytes` give these figures for a plan.

| Stage | Peak | What is live |
|---|---|---|
| Decode one frame | decoded image 3 to 8 (Rgb8 3, Rgba8 4, Rgb16 6, Rgba16 8) + planar frame 12 | a copy to RGB is made only when the source is not already RGB8/RGB16 |
| Alignment, per frame | about 39, independent of `N` (`TiledPlan::align_ram_bytes`) | the reference (12, held for the whole pass), the frame (12), and the refinement working set (two luma pyramids at about 5.3 each and a warped luma plane at 4) |
| Alignment, `chain_alignment` | **+18** | the raw previous frame (12) and its luma pyramid (6) |
| Alignment, look-ahead | **+12 per waiting frame** | with a seed source (AKAZE matches, network matrices) the window holds `min(threads, 8) - 1` frames beyond the one in flight; none on `wasm32`. `align_into_store_overlapped` adds **12** for the frame its decode thread holds, with or without a seed source |
| Tile store (disk) | `12 * ((T + 2A) / T)^2` per frame | one file per padded tile: 27 at `A` = 128 and `T` = 512; **108** at the `Apex` default (`A` = 512, `T` = 512); 13 for `Relief` at the default radii (`A` = 10) |
| Auto-cull census | `16 * Q` for one padded tile and its focus map (4), plus 8 | the winner map (an `f32` score and a `u32` index per image pixel) |
| `Relief` threshold pass | `N * 12 * Q` plus **10 * Q**, plus 4 | one padded tile (12) of every frame, the folded best-focus and winner planes (6) and one focus map in flight (4), plus the whole-image maximum focus map (`f32`) |
| Fusion, `Apex` | `N * 12 * Q` plus **96 * Q** (the fold at its upper bound of 12 levels; 84 at the default 8) | the tile of every frame, and one accumulator pyramid, the `best_energy` planes, the incoming frame's pyramid and the build transients: the frames are folded in one at a time, so no pyramid is kept per frame |
| Fusion, `Relief` | `N * 12 * Q` plus **10 * Q** (`fusion_ram_bytes`) | the tile of every frame, and the best-focus plane (4), the winner index (2) and the focus map in flight (4): the maps are folded in as they are computed, none is kept per frame |
| Fusion, `Relief` with multigrid | votes pass: `12 * Q` plus **10 * Q** (one frame at a time) plus **6** per image pixel; solve: **28** per image pixel (+4 for the best-focus map while the threshold is decided), no frame in memory; composite: `N * 12 * Q` plus **4** per image pixel (the depth) | the winner planes, then the depth map |
| Fusion, `Strata` | **174 * Q** whatever `N` (150 for the accumulators, winner map, prepared planes, weights and guided-filter scratch, plus the two tile frames it holds at a time, 24) | the frames are read on demand, two at a time, in two passes |
| Read-ahead of the next tile (`Prefetch::Auto`) | **+ `N * 12 * Q`** (`TiledPlan::prefetch_extra_bytes`); none for `Strata` | a second thread reads the frames of tile `t + 1` while tile `t` is fused, whenever the frames can be shared, the run has more than one tile and the caller is not a rayon worker. The result is identical to `Prefetch::Off`; this is the price |
| Output buffer | **3** (8-bit) or **6** (16-bit) | the only full-image allocation of the fusion pass; cropping copies it once more at save |

Example: 100 frames of 24 MP at `T` = 512 with the `Apex` default (`A` = 512): the store needs 100 * 24 M * 108 B, about 260 GB of scratch disk, and the fusion pass holds `100 * 12 * 1536^2 + 96 * 1536^2`, about 3.1 GB of RAM per tile (twice the frame part, about 5.9 GB, while the next tile is read ahead). Both fall by an order of magnitude with `pyramid_levels = 6` (`A` = 128: 27 B/px, `Q` = 768^2), and `Relief` needs far less (`A` = 10). The CLI logs the padding factor and the scratch bytes per source pixel before it starts, and warns when a stored tile is more than 4 times its interior.

### Desktop app (in-memory)

| Stage | Peak per pixel | What is live |
|---|---|---|
| Load | `12 * N` | the planar frames only (no RGBA copy); decoding runs in parallel, so a few extra decoded images are transient |
| Align | `12 * N` plus the working set of the frame in flight (29: the aligned frame, the refinement pyramids and warped luma, the coverage masks) | the reference is moved out of the list, not cloned |
| Align, `chain_alignment` | **+18** | the raw previous frame (12) and its luma pyramid (6) |
| Align, look-ahead | **+12 per waiting frame** | with a seed source (AKAZE, network) the window holds up to 7 frames beyond the one in flight; none on `wasm32`. The in-memory driver does not decode on a second thread |
| Align cache | `12 * N` | kept in the app state after the Align button; a Stack run that reuses it clones the frames (another `12 * N`) |
| Cull | about `16 * N` | the frames (12) and one focus map per frame (4) (`optimize_stack`) |
| Fusion, `Apex` | `12 * N` plus **84** at the default 8 levels (`stacker_algo::apex::fuse::apex_fold_bytes_per_pixel`) | the frames, and one accumulator pyramid, the `best_energy` planes, the incoming frame's pyramid and the build transients: the frames are folded in one at a time, flat in `N` |
| Fusion, `Relief` | `12 * N` plus **62** | the frames, the maximum map (4), the winning frame (2), the mask, the selected image, the guided filter's temporaries and the result; the focus maps are folded in as they are computed, none is kept per frame |
| Fusion, `Relief` with multigrid | `12 * N` plus **62 + 36** (the solver's 28, the depth 4 and the best-focus map 4) | the winner planes, then the depth map |
| Fusion, `Strata` | `12 * N` plus **150** | the frames, the accumulators, winner map, two frames' prepared planes, the refined weights, filter scratch and the output or preview snapshot |
| After an earlier pass | **+12 per earlier pass** | the earlier result stays in memory while a later pass fuses (`estimate_peak_bytes` with several `PassKind`s) |

The desktop app holds the whole stack, so its peak is the larger of cull and fusion per frame, plus the Align cache when it is alive. The CLI trades that for scratch disk. The fused planar result also stays in memory (12 per pixel) as the base of the retouch session.
